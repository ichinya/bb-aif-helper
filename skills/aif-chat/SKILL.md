# AI Factory Chat

## AI Factory 2.22

Read canonical plan settings and task-kind/outcome markers. A skipped checked task is not an executed task, a commit receipt is not a task checkbox, and metadata is not execution evidence. Deferred commit strategies and pending marked commit tasks stay with aif-implement: do not bypass them with generic aif-commit. Respect workflow.fix_mode and the independent boolean workflow.fix_patch; do not add per-call override flags implicitly.

The plugin recognizes only registered, project-contained shared skill links to the same skill in .agents/skills. New installs/updates retain the chosen symlink mode. Devin/Windsurf project runtimes can be selected explicitly; home directories are not scanned.

Coupling is an explicit optional review +coupling action. Last-reply suggestions retain discovered invocation arguments, including this modifier and planning mode. Plain review evidence does not attest coupling analysis. Worktree diagnostics use ai-factory worktree-check --json for the current checkout, only with a known compatible CLI; no environments are launched and static results do not prove runtime isolation.

Completion-hook metadata only declares a setup; it is not current PASS or an authenticated receipt. AI Factory 2.22.0 supports its Claude Code 2.1.318 adapter on Linux/macOS. Do not invent a completion-hook status subcommand, enable the integration, or run a verifier as part of display/update. Any explicitly requested setup remains opt-in and owned by the installed CLI contract. Preserve the CLI → project → extensions update sequence and daily version cache.

## Navigation for unfinished plans

For an OpenSpec SessionBrief stale/missing/research/invalid/blocked report, preserve the context blocker and offer scoped mode sync and SessionBrief compile separately. The plugin remembers the latest plan-bound root reply across reloads; an unrelated message or exit 0 does not clear it. A later bound valid/fresh report (or constrained native result JSON after the matching CLI request) can restore navigation, but it is still a chat claim, not proof of current inputs or PASS. The installed implementation owner must verify actual context before proceeding. Never bundle implementation into context repair or interpret a change to another plan as recovery. The SessionBrief CLI suggestion is allowlisted, change-bound and requires a healthy registered wrapper file. Display reads never import extension JS or invoke the compiler.

For a selected unfinished ordinary plan, keep both implementation and repeatable improvement visible. A stale unknown/plan/explore phase does not prove that improvement has never happened. Do not infer a completed improve run from file timestamps, command counts or a declared phase, and do not force an improve rerun to expose implementation. The implementation owner still checks all required handoffs, sync, readiness artifacts and blockers. Preserve the separate fix-plan owner, post-fix verification, completed-plan finalization, busy/pending and missing-skill guards.

## One transcript card per thread

Only the newest card issued by `aif_chat_status` or CLI `show` remains rendered in a thread. Use the returned directive unchanged, including its generated `card` identifier; do not reuse an older directive or invent identifiers. Ordinary `status` reads do not replace the card. A suppressed output while awaiting an answer also leaves the latest identifier unchanged.

Previous card blocks and legacy directives without identifiers are hidden in the transcript. Their surrounding messages remain intact. Superseded cards unmount their workflow status reader and stop polling; the latest identity survives plugin reloads and is scoped to its thread/environment. The persistent panel remains available independently of transcript cards. This does not delete conversation history or gate data.

## Waiting for a user answer

An improve reply that explicitly asks to apply its proposed diff can expose a composer button labelled "Применить всё". It requires a matching preceding aif-improve launch for the selected plan and a latest completed root reply, not quoted examples or child messages. Only clicking that button supplies confirmation for those proposed plan edits; do not infer consent from its presence or run implementation. The plugin revalidates proposal identity, selected plan/files and thread state, and sends one visible scoped confirmation without a hidden prompt. Changed proposals require new confirmation. Native BB interactions still require their own answers; the shortcut cannot answer or bypass those forms.

Do not call the status tool or append a workflow card when asking the user to confirm a research scope, approve a plan or answer a clarification. This often happens after preliminary exploration: the next step is the user's answer, not another workflow action. Existing authorization still applies; this rule does not require a new approval question.

The UI hides transcript cards while BB has an open interaction or the latest unanswered root reply explicitly requests confirmation. The persistent panel keeps read-only progress and names the waiting state, with actions disabled. Text detection ignores quoted instructions, code, examples and child-agent messages; it is a navigation heuristic, not a permission system. A newer user turn clears the old wait regardless of whether the answer agrees, refuses or changes scope. Clearing it does not execute a command or grant permission; interpret the actual answer normally.

If the status tool reports `awaitingUser: true` or an empty `previewDirective`, emit no directive. Failed question-state reads do not authorize a button dispatch. Never replace a required skill question with workflow buttons or manufacture a yes/no form.

## Projects without AI Factory

A missing/deleted basic plan is stale navigation, not a broken project setup. Release the old selection and cached accepted-plan context, keep exploration and native planning available, and do not substitute another file or start work automatically. Invalid configuration and unsafe paths remain guarded.

The selector shows each plan's completed/total count. Nonempty basic plans are hidden by default when every task checkbox is complete, independently of verification. Classic plans are hidden only when their companion status.yaml declares status: done and its plan_id and any plan_file/artifacts.plan references match the candidate. Checkbox completion alone does not close a classic plan. The view-only “Показать завершённые” toggle restores hidden plans; files are never deleted. Unchecking a basic task or reopening classic status returns the plan to the active list. This navigation filter never declares PASS; OpenSpec and other AI Factory formats keep their own lifecycle. After actually passing every required check and completing all tasks, the verification owner may run `bb plugin run aif-chat mark-verified --target <exact plan path>` in the same thread. It writes a leading bb-aif-plan-verified marker bound to the plan contents, not a proof of code/CI PASS. Never mark on generation, findings, NOTRUN or UNKNOWN. Any plan edit expires the marker. Do not mark pre-existing plans merely because their checkboxes are checked.

A completed root plan after builtin Plan is exported to `.bb/aif-helper/plans/` by the plugin after generation. Emit the full Markdown document inside one four-backtick `aif-plan` fence (inside proposed_plan if the provider requires it): heading, goal, constraints, `## Tasks` with numbered unchecked tasks, checks and completion criteria. The renderer displays a styled document and file link, then its workflow form after completion and successful saving. Do not call aif_chat_status to emit a form before the plan or append a directive after proposed_plan. The plugin saves outside the agent's Plan restrictions; never write project files from Plan mode. Old raw proposals can be saved with `bb plugin run aif-chat save-plan --thread <id>`. Incomplete/stale answers do not save, errors keep the original reply, and retries never overwrite task edits.

When the project has no AI Factory setup (profile none), the panel offers a separate installer and a bundled exploration → native BB Plan → implementation → verification → commit workflow. Planning sends BB's builtin `/plan` command mention, just like the composer Plan action, after checking provider support. Other actions send human-readable requests plus agent-only instructions to the current agent, not unavailable skill invocations. Opening the panel runs nothing. Exploration is read-only and uses bundled guidance adapted from upstream aif-explore; no remote prompt fetch is needed.

The bundled **Исследовать задачу** button first opens an inline description form. The user supplies a question, problem or issue link (up to 4000 characters), then explicitly starts research or cancels. Opening/cancelling the form sends nothing; the server rejects a missing description. The description appears in the visible request, while the bundled read-only instructions remain agent-only. A failed send keeps the draft. This input is the task for exploration, not permission for implementation or installation.

The basic planning button explicitly selects native Plan mode; respect that mode's restrictions. Saving a generated document never starts implementation. File plans under `.bb/aif-helper/plans/<slug>.md` and legacy `.bb-aif-helper/plans/<slug>.md` are readable by the panel; their implementation follows the selected tasks. Completed basic plans offer a separate new-task exploration form. Only successful submission releases the old selection and declares exploration; preserve the old plan and use the new description as scope. Report that exploration with phase explore and no target. Verification reports actual checks and NOTRUN/UNKNOWN, and commit preserves unrelated files and existing authorization boundaries. Each click authorizes only its chosen step; never start the rest of the chain implicitly. Do not change permissions or invent PASS/evidence from checkboxes.

The installer reuses an existing CLI or installs it through its normal package manager, initializes the selected supported runtime, and verifies metadata/skills. It must not add MCP/extensions, replace a linked CLI, overwrite user files or start workflow implicitly. After successful setup, the managed basic selection is released; existing plan files remain, with no automatic migration. Invalid existing installation/configuration stays guarded rather than falling back around its owner gates.

## Installed workflow

The persistent **AI Factory** button in the thread header opens the workflow tab in the right panel; on narrow layouts BB moves it into the header menu. Opening this panel only reads status and never dispatches a workflow. Users do not need to find a previous transcript card. The panel follows the owning thread and its stored selection/phase.

The panel uses a persisted SQLite snapshot cache: saved data may appear immediately while revalidating in the background. The footer shows the data source and collection time. Ordinary display can reuse a snapshot for one minute; busy state and questions are read separately. The refresh button, native status tool/CLI and action dispatch force fresh file reads. Never describe a saved/cached snapshot as newly verified evidence. Refreshing the cache does not run a model, workflow or automatic GitHub query.

CLI/source versions use a separate 24-hour saved cache; ordinary force reads do not bypass it. Project and extension metadata still come from ordinary workflow reads, and extension versions are shown in the short version line. Explicit maintenance invalidates local version samples so the final status can show the updated installation. GitHub checks are opt-in and limited to one saved attempt per host/repo/ref per 24 hours, including failures and reloads; no force retry bypasses that external limit. With matching known versions, updater buttons move under "Версии и расширения"; mismatches and broken extensions keep the relevant updater above the fold. The section shows collection time and next external-check time. Do not infer that a missing top-level updater proves a freshly checked latest release.

The composer recognizes both `$aif…` and `/aif…` commands in the last assistant answer and displays the current runtime's prefix. Discovered arguments, flags, quoted paths and issue references are retained within that invocation. Markdown backticks, following commands, shell statements and surrounding prose are not arguments. Incomplete quoted or oversized argument lists are omitted rather than sent with a silently reduced scope. Paths and URLs are not skill invocations. A click sends only one visible text block with the command and its arguments, without an additional or hidden prompt. Gate data stays in the existing conversation/UI, and all server-side workflow guards still apply. The × control hides one suggestion without a message or workflow action. Suggestions preserve the user's draft and revalidate the answer and workflow guards on the server. Do not emit special markup just to populate this row or run every suggested command automatically. When suggesting the user's next command, write it in full inside inline code — for example `` `/aif-fix fix the login crash` `` — so the chip carries the arguments; a bare name in prose loses them. Arguments inside `<...>` are dropped by the parser; the chip then takes its topic from the gate `suggested_next.reason`.

The final `aif-gate-result` is parsed separately: declared status, blockers, affected files and the allowlisted `suggested_next` are shown above the composer. Non-blocking WARN can suggest commit; blocking or malformed gates cannot authorize advancing to commit/done/archive/implement through plugin buttons. The selected skill receives normalized gate data as untrusted context and must recheck freshness. Preserve the original machine-readable output contract, including the final-block position; never append a chat directive after it just to update this UI.

If valid gate JSON is followed by extra prose, the client shows a separate format warning while retaining the declared result and an allowed remediation such as aif-fix. Trailing prose is never handoff input. This does not relax the final-block contract: implementation, commit and finalization remain blocked, even for PASS, and the result does not establish current-input freshness. Keep gate last when generating a response; malformed JSON or contradictory gate fields remain errors.

In the transcript, the JSON fence is collapsed under "Данные gate" by its code-fence renderer. Expanding it shows BB's original code block and copy control. Keep emitting the required gate JSON unchanged: this is a presentation feature, not permission to omit the machine-readable result. Malformed or interrupted gates still show a visible error.

The checks table also restores completed gates from thread history, scoped to an explicit canonical plan path in affected files or the preceding launch request. Each gate retains its last discovered result across later replies and plugin reloads. `WARN/PASS/FAIL · из чата` records the declared historical outcome with time and message sequence; it does not create a report file, attest current inputs, or satisfy workflow readiness. Keep that distinction when reporting status. A command launch or prose PASS alone is not a completed gate.

Check buttons are beside their rows. On a live completed verify/rules/security/review, the plugin may bind the declared result to an observed workspace fingerprint. Matching inputs disable repeat buttons with "без изменений"; changed inputs enable them again. Old results and unavailable fingerprints remain unknown and never acquire today's fingerprint just by opening the panel. This comparison is a navigation guard, not proof of fresh PASS. An explicit user request to recheck still authorizes the skill normally; do not infer completion from a disabled button.

Use native tool `aif_chat_status` with the selected project-relative plan/change entrypoint and the phase actually reached (`explore`, `plan`, `improve`, `implement`, `verify`, `fix`, `done`). Emit its `previewDirective` exactly once on its own line, outside code. It renders an interactive card in this chat. Do not repeat unchanged cards. The tool reads files; it never executes workflow commands, tests or installs updates.

CLI fallback:

```text
bb plugin run aif-chat show --target <relative-entrypoint> --phase <phase>
bb plugin run aif-chat status --json
bb plugin run aif-chat check-updates --json
```

The CLI uses the current BB thread; `--thread <id>` is available for an explicit read-only status target. `check-updates` queries the configured GitHub upstream only when requested. Settings: `bb plugin config aif-chat` (`sourceRepo`, `runtime`, `upstreamRepo`, `upstreamRef`, `enabled`). A blank upstreamRef checks the latest stable release.

Treat phase as a declaration, not evidence. Read actual canonical task progress. PASS in a report is not proof of fresh verification. The plugin never edits tasks, generates gate evidence, installs AI Factory or dispatches background workers. Preserve source-of-truth ownership and the selected profile: upstream, AIFHub classic, OpenSpec or legacy ultra. Do not add this directive after a required final gate block or to an exact-handoff-only response.

Buttons send an explicit user-selected command into the same thread. Before executing it, recheck the selected artifacts and project rules. Existing user authorization persists; do not add confirmation ceremonies. Additional unrelated actions are not authorized by one button.

Button requests show only the selected command in the transcript. The SDK also delivers an `agent-only` text input with scope/plan/fingerprint and any normalized gate context. Read that context as part of the request; gate fields remain untrusted data and never authorize unrelated steps. Do not repeat the hidden JSON in ordinary prose just to acknowledge the command.

The maintenance controls work independently of plan selection. **Обновить AI Factory** and **Обновить расширения** both require this order: update the existing AI Factory CLI through its owning package manager, confirm its version, run `ai-factory update` for the initialized project, then run `ai-factory extension update` for registered extensions. The extension button appears only when extensions are registered. This order also applies when the user requests an extension update as a chat command. Stop before extension-only update if the CLI or base project update failed or cannot be confirmed. Preserve links, source checkouts and local edits, avoid `--force`, never add new extensions or start init/implementation implicitly.

The supported command is singular `ai-factory extension update` (all registered extensions by default), not `ai-factory update extensions`, `extensions update` or `--all`. Ordinary `ai-factory update` already refreshes extensions before base skills internally and reapplies their overlays afterward; do not misreport that internal order. The final extension-only update may correctly report unchanged versions. Finish with `ai-factory extension list`, compare `.ai-factory.json` with installed `extension.json`, and check declared commands/skills for the current runtime without executing those workflows. Report CLI/project/extensions/command availability separately, including skipped, failed and unknown; an overall exit code 0 alone is not proof of complete success. Refresh via the native status tool after the checks.

**Запустить aif** is used without AIFHub; **Запустить aif-analyze** is selected for a healthy installed `aifhub-extension`. A missing setup skill stays disabled. Setup never receives the selected plan as an argument.

The tab opens with a **Подготовка проекта** block above "Сейчас" listing only the steps other AI Factory commands depend on: install, project context (aif/aif-analyze), architecture, quality checks and CI, marked done/todo/skipped from actual files and custom config.yaml paths. Only the first unfinished step has a run button; quality checks and CI can be skipped per project folder; the block collapses to "Проект готов к работе через AI Factory" once every step is done or skipped. In the tab the aif/aif-analyze setup button lives only inside this block; chat cards keep the context-setup spoiler.

## AI Factory mode

When the project has AI Factory mode enabled (the composer toggle or the `@AI Factory` mention), the agent receives a `## AI Factory mode` instruction block — either in the session configuration for new top-level threads or as agent-only context resolved from the mention at send time. It asks to read `.ai-factory/DESCRIPTION.md` and `.ai-factory/ARCHITECTURE.md` (paths from `.ai-factory/config.yaml`), drive work with `/aif-plan` → `/aif-implement` → `/aif-verify` → `/aif-commit` (`/aif-fix` for bugs), follow `.ai-factory/skill-context/`, and call `aif_chat_status` at workflow boundaries. The mode is a suggested path, not a ban: an explicit owner request to do otherwise wins. Child threads never get it — they carry their own briefs. The plugin never inserts the mention by itself: a running session that started before the mode was enabled, or an ACP session after a compaction, gets the mode text only when the owner types `@AI Factory`. Treat a repeated mode block as the same instructions, not a new task. A typed mention is removed from a `/aif-…` or `$aif-…` command draft so it never becomes a command argument.

## Code delegation

The tab splits into **Навигация** (current work) and **Настройки** (one-time setup) via a switch in the sticky header, remembered per thread for the browser session; message cards have no switch. In **Настройки**, the **Исполнители** section lists four one-line roles — **Код**, **Разведчик 1**, **Разведчик 2**, **Разведчик 3** — each showing the current model with an «Изменить» button that expands the «Этот агент / Другая модель» editor; explanations sit under «?». **Код** picks who writes code for plan tasks: this chat's agent or another BB provider/model/reasoning level. Saving writes `.ai-factory.json` → `phases.implement` (`agent: "bb"`, `model: "provider/model[:effort]"`) and a managed block in `.ai-factory/skill-context/aif-implement/SKILL.md`. That block tells `/aif-implement` how to delegate with native BB commands: write the task brief to a temporary file, reuse a non-archived child thread titled `AIF · <plan> · <taskId>` or spawn one with `bb thread spawn` on the panel's provider/model/reasoning/tier, wait with `bb plugin run aif-chat wait-worker --worker <id> --json` (repeat with `--after <seq>`; an idle worker with an interim report such as "waiting for the tests" still works), review the diff, verify, then mark the task. One worker at a time; workers share the chat's workspace and never edit the plan, commit or push. With **Параллельно** (2–4) enabled on **Код**, the managed block instead makes the coordinator follow AI Factory's `implement-coordinator`: it reads the plan itself, builds layers from `(depends on …)` and phases, writes `<!-- parallel: tasks N, M -->`, `[~]` and `[!]` marks into the plan, and start each layer task's worker under the `implement-worker` contract with `bb plugin run aif-chat spawn-worker --target <plan name> --task <id> --brief '<absolute brief path>'` (BB makes a git copy of the whole repository from HEAD plus the coordinator's uncommitted work, without touching its index, through the `aif-chat-worktree` environment provider, also for a section inside a larger repository, and removes it five minutes after the worker is archived), and bring results back one by one with `bb plugin run aif-chat bring-back --worker <id>` (`git apply --check`, then `git apply`, never `--3way`; a refused patch changes nothing) with per-task verification; failures are analysed and retried up to three times per cause before asking the owner; no path, JSON or `git status` output passes through the coordinator's shell; no intermediate commits are made, the coordinator commits only where the plan says; commit/deploy tasks stay with the coordinator and single-task layers use the one-worker flow. The plugin does not parse plans. The config file is the source of truth: if `phases.implement` no longer says `agent: "bb"`, implement tasks yourself. After a plugin update the managed block is rewritten to the current text the next time the panel or `aif_chat_status` reads the project, which leaves an uncommitted change in `.ai-factory/skill-context/`. A `phases.implement` owned by another agent is shown and never overwritten. Switching back to this agent removes only what the plugin added. **Разведка** picks the model for research subagents of every AI Factory skill: saving writes a managed block to `.ai-factory/skill-context/global-skill-context.md` (first line `<!-- research-model: provider/model?… -->` is the source of truth). When a skill asks for Explore/research subagents, spawn read-only BB child threads titled `AIF research · <skill> · <topic>` on that model in parallel, wait for them and use their reports; `.ai-factory.json` is not touched. There are three research workers, numbered in the order the skill lists its subagents: 1 — architecture/affected modules (also the only one when a skill asks for one), 2 — patterns/conventions, 3 — dependencies/integration (and any further workers). Each has its own marker (`research-model`, `research-model-2`, `research-model-3`); workers 2 and 3 fall back to worker 1, and the block lists the spawn flags per worker. Below the roles, the collapsed **Модели по умолчанию для новых проектов** block stores plugin-wide defaults in `bb.storage.kv` (`delegation-defaults`), shared by all projects and machines of this BB install; «Взять из этого проекта» copies the project's four roles, «Применить к этому проекту» writes them immediately, «Очистить» removes them. In a configured project where all four roles are «Этот агент», the server auto-applies the defaults once through the same files a manual save writes (`.ai-factory.json` → `phases.implement` and the skill-context blocks), marks the project with `delegation-defaults-applied:<hostId>:<path>`, and reports «Применены модели по умолчанию: …»; it never re-applies, any manual role save also marks the project, and a foreign `phases.implement` is left untouched (only research roles apply). This leaves uncommitted changes in the project repository — surface them, do not commit silently.

## Optional workflow checks

When the current project Git status confirms uncommitted tracked, staged or non-ignored untracked files, the card offers aif-commit first even after archive, with no active plan or multiple plan candidates. Unknown/clean status does not create this extra offer. This is separate from sourceRepo version dirtiness. Opening the card does not commit anything. A selected commit request must inspect the actual diff, determine the task scope, preserve unrelated files, obey gates and existing commit permissions, and never implicitly authorize push.

Rules, security, review, QA preparation/execution, quality audit, existing CI inspection and OpenSpec mode doctor are supplementary navigation branches, not an automatic chain. Their buttons stay beside their check rows. Mark them as optional only when no known required policy applies; project/skill requirements always take precedence. Skipping an optional check does not invent a failure, while an actual blocking FAIL still prevents advancement. Do not classify verify, coverage or done readiness as optional merely because they appear in this section.

OpenSpec mode diagnostics use `aif-mode doctor --change <id>` for the selected canonical change. This is separate from mandatory readiness inside done and does not authorize sync, init, --fix, providers setup or finalization. Doctor is not offered for upstream or legacy ultra.

## Existing CI inspection

If invoked as `aif-chat ci`, inspect the existing CI pipeline/run for the current Git HEAD through the project's existing connector/CLI. Report commit SHA, run URL and per-job outcome. Do not generate pipeline configuration, push commits or trigger/retry workflows just to inspect their status. If no provider or run is available, say UNKNOWN/NOTRUN and give the smallest next action. Then refresh the card without inventing a green CI result.

## Delivery recovery

`bb plugin run aif-chat reset` clears only this thread's UI selection/declared phase. `reset-dispatch` clears delivery history only after the user has inspected an uncertain send and explicitly requested recovery. Never reset it automatically or retry an ambiguous message delivery. Project artifacts are unaffected.
